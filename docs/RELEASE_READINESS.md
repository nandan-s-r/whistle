# Whistle release preparation — 5 October 2026

This is a verified local candidate, not a published release or security certification. No GitHub push, Vercel deployment, account migration, provider purchase or outbound message was performed.

## Account choice and retained work

Use **Cloud account** for the hosted product. Create an account with your own email/password, confirm the email, then sign in with the same cloud credentials next time. Supabase stores the cloud identity and the organization/owner-scoped research. The Gemini API key is a server setting, never a login password. Password recovery starts with **Forgot password** after entering the email; the reset link must be opened in the requesting browser for PKCE.

**Local preview account** is explicitly separate. Its users and research live in the local database; the same email does not merge it with a cloud account. A stable private `JWT_SECRET` and persistent database keep returning local sessions usable. Tokens expire after seven days; passwords remain stored as bcrypt hashes. No user records are copied between modes automatically. This preview retained its existing account and 13 records after restarting both services.

In Supabase Auth URL configuration, set the actual deployed frontend origin and allow its `/auth/confirm` and `/reset-password` URLs. For local cloud testing, also allow `http://127.0.0.1:3000/auth/confirm`, `http://127.0.0.1:3000/reset-password`, and equivalent localhost URLs. Keep hosted email confirmation enabled; configure a production mail service and test signup, confirmation, recovery, logout, returning sessions and two-user access. No real confirmation/reset email was sent during this verification, and hosted Auth settings were not changed.

## Vercel frontend and API host

Import this repository with Vercel's root directory set to **frontend**. Use the lockfile, `npm ci`, and `npm run build`. Configure `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` for the same Supabase project used by the backend. Set the server-side `BACKEND_URL` to the actual HTTPS API. Production builds now refuse a missing or unsafe backend URL. Leave `NEXT_PUBLIC_LOCAL_AUTH` unset/false for the hosted build. Rebuild after changing public settings.

Run the API separately using `backend.main:app`, `ENVIRONMENT=production`, `AUTH_PROVIDER=supabase`, the same `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, and the actual `FRONTEND_URL`. The Vercel frontend does not run the Python background worker. Use `Dockerfile.api` and `compose.yml` for the intended container configuration; `docker-compose.yml` is the older development configuration. Redis, worker and scheduler need a deliberately configured host. Configure `JOB_DATABASE=supabase` and the private service-role key only for the trusted worker. Enable `FUND_ACCESS_ENABLED` only after testing the fund migrations with actual separate users. Render's free service can cold-start; hosted latency is not established by the local build.

Store Gemini, Firecrawl, X and service-role credentials only in private backend/worker settings. Never use a `NEXT_PUBLIC_` name for them. Industry research uses `GEMINI_API_KEY` and a configured `GEMINI_MODEL`. Sourcing's Firecrawl adapter requires a separate runtime `FIRECRAWL_API_KEY` and credits; the chat MCP connection does not transfer a credential to Whistle. Official X access requires `X_BEARER_TOKEN` and an appropriate entitlement. Calendar export is implemented; authenticated Calendly/calendar synchronization is not connected. Apollo access is blocked by the current plan; commercial data licensing remains separate.

## Verification and remaining release gates

The selected Calendly adapter is now implemented for an explicitly bound internal account, using private `CALENDLY_ACCESS_TOKEN` and `CALENDLY_ACCOUNT_SCOPE` settings. It has not been activated against a live calendar. Use read-only user/event scopes and the account scope shown in Connections; keep credentials server-side. Public multi-customer release needs per-user OAuth instead of a shared PAT. Verify actual provider consent, changed/cancelled bookings, duplicate import and separate-user calendar/deal isolation before calling it operational. See INTEGRATION_WORKFLOWS.md. The latest integration suite passes 173 backend tests; prior dated results below remain historical.

Industry research now checks available sources for the authenticated account, allows public Product Hunt/GitHub searches independently of Gemini, and keeps their results when another source fails. The frontend proxy timeout is 90 seconds to accommodate the existing cloud allowance check and bounded provider calls. Before hosted acceptance, sign in as an actual cloud user and run a non-confidential prompt with explicit consent; require a completed cited Gemini answer. Key detection alone does not pass this gate. Confirm licensed social/provider coverage separately. The final unified-search regression is 162 backend tests; dated earlier security/test counts below remain historical.

The source/filename check reports no credential-like literals or tracked private configuration among inspected source/document files; it deliberately never opens private settings, key files or databases. It is a limited pattern check, not proof that Git history or every secret type is clean. Run `python scripts/check-release-secrets.py` before pushing. GitHub verification now includes it. Review all existing working-tree changes before creating a commit; this checkout already contains substantial earlier work.

The frontend production dependency audit returned zero known advisories. A deeper resolved Python audit initially found the unfixed `ecdsa` signing advisory through `python-jose`. Whistle uses HS256 locally and delegates cloud verification to Supabase; affected EC signing was not demonstrated as reachable. The unnecessary dependency was removed by migrating to pinned `PyJWT[crypto]==2.15.1` in all three requirement sets. The final resolved API/development set contains 55 packages, no `ecdsa`, and zero known advisories. Existing standard HS256 sessions, expiration, signature/algorithm/audience rejection, account revocation and hybrid cloud authentication pass the 153-test backend suite using the actual pinned token package. A fresh independent source review approved the migration. The preview uses the isolated tested package; the global Python installation was not modified. New installations must install the current requirements into an isolated environment.

GitHub verification now runs the resolved Python advisory audit as well as frontend checks. The local resolution used Windows/Python 3.11; a fully resolved, hashed production Linux/Python 3.12 lock remains release work. Docker execution and remote CI, Vercel, HTTPS, email delivery, live worker, telemetry, storage-through-app and multi-user hosted acceptance still require verification. Preserve secrets and database backups outside Git; set retention and recovery policies with the operator.

The security review contains a malformed-shared-record availability issue in isolated fixtures. Aggregate workspace/search/intake now quarantine invalid authorized records instead of failing all records. History and access administration remain available; direct use returns a repair message. This is containment, not automatic data repair or a database-wide JSON schema guarantee. Do not silently overwrite or delete the damaged record. Authorization, grants and RLS remain intact.
